## 〇、一句话结论

**这是一个"架构判断正确、工程质量高于平均水平、但交付纪律有硬伤"的项目。**

- 安全设计的骨架是对的，而且是被实测验证过的：白名单冻结、路径重编码、Origin/Host/CSRF 四重校验、凭据不下浏览器、容器加固，生产模式下的安全头与 Cookie 属性全部实测相符。这一类"看起来对、实际也真的对"的中间层项目并不多。
- 契约基线（237 op / 175 path / 495 schema / 24 router / 76 条白名单）**完全真实、可逐条复算**，不是编的。双仓交叉核对后差异为 0。
- 但存在 **2 个必须立刻处理的问题**（源码泄露、公开仓库泄露真实基础设施拓扑）、**一组实现级缺陷**（其中 1 个未认证即可触发的 500）、以及**严重的文档腐化**（四份验收文档互相矛盾，数字有 6 种口径）。

如果这是要交付给客户或开源的东西，我的建议是：**先处理 P0 的 2 项和文档矛盾表，再按 P1 顺序修 3~5 处代码，其余可以排期。**

## 二、必须立刻处理（P0）

### P0-1 生产源码全量泄露：7.28 MB sourcemap 可被未登录下载

**实测**：`apps/web/dist/assets/index-VdWscvgz.js.map` = **7,283,343 字节**；生产模式启动真实 BFF 二进制后 `GET /webui/assets/index-VdWscvgz.js.map` → **200**，`cache-control: public, max-age=31536000, immutable`，响应体首段即 `{"version":3,"sources":["../../../../node_modules/.pnpm/react@19.3.0/...`。

`node -e` 解析后：`sources: 990`，`sourcesContent` 990 条，总字符 4,586,166 —— **是完整前端源码（含注释），不是只有映射表**。再加上 `apps/bff/dist` 里另有 17 个 `.map`，map 占产物总量的 81.3%。

三处根因叠加：
1. `apps/web/vite.config.ts:29` `sourcemap: true`
2. `tsconfig.base.json:19` `"sourceMap": true` 被 `apps/bff/tsconfig.build.json` 继承
3. `Dockerfile:97-98` 整目录 COPY，`.dockerignore` 无 `.map` 规则，`nginx-webui.conf` 也不拦 `*.map`

**影响**：任何能访问 `/webui/` 的人（不需要登录）可下载全部前端源码。不含密钥，但内部逻辑、注释、接口结构全暴露，外加 7 MB 带宽。缓存头是 1 年 immutable，意味着**即使你明天修了，已经拿到的人不影响，CDN 也会继续供给**。

**修法**（任选，建议 1+3）：
1. `vite.config.ts` 改 `sourcemap: 'hidden'`，或构建后删除 `**/*.map`；
2. `apps/bff/tsconfig.build.json` 加 `"sourceMap": false`；
3. BFF 静态托管对 `.map` 直接 404（`apps/bff/src/routes/health.ts:57-78`），或在 `.dockerignore` 加 `**/*.map`。

## 三、应该修（P1）

### P1-1 未认证即可触发的 500：畸形 JSON 漏映射

`apps/bff/src/server.ts:117-144` 的 `setErrorHandler` 映射了 `FST_ERR_CTP_BODY_TOO_LARGE`→413、`INVALID_MEDIA_TYPE`→415、`EMPTY_JSON_BODY`/`VALIDATION`→400，**唯独漏了 `FST_ERR_CTP_INVALID_JSON_BODY`**（fastify 5.12.5 里 status 400）。

**实测复现**（development 与 production 都复现）：`POST /webui/bff/auth/login`，正确 Host/Origin/CSRF，body `{bad json` → **500** `{"error":{"code":"WEBUI_INTERNAL",...}}`。

影响：任何客户端发语法错误 JSON 就得到 500；未认证即可触发 `app.log.error` 污染日志；全部写接口（login/logout + 73 条代理写）同受影响。而 43 个 BFF 测试里**没有一个**畸形 JSON 用例。

**修法**：并入 `FST_ERR_CTP_EMPTY_JSON_BODY` 分支 → 400 `WEBUI_INVALID_REQUEST`，加一个测试。约 5 行。

### P1-2 "绝对 8 小时"会话上限形同虚设

`apps/bff/src/auth/session-store.ts:199`：
```ts
session.absoluteExpiresAt = Math.min(now + this.config.sessionMaxSeconds * 1000, absolute);
```
用的是 `now` 而不是 `createdAt`，所以每次上游刷新都会把绝对期限往后推。唯一调用点是 `apps/bff/src/auth/controller.ts:326-339`（距上次刷新 >60s 即触发）。

**实测**（直接 import 编译产物驱动 `SessionStore`）：创建时 8.00 小时；T+7h 刷新一次 → **15.00 小时**；T+14h 刷新 → **22.00 小时**；每 61s 刷新持续 23.7h → **31.72 小时**。

影响：`WEBUI_SESSION_MAX_SECONDS` 配置项失去意义，与 `session-store.ts:7` 头注释和 `docs/security-model.md` 的会话模型都不符。修法：以 `createdAt` 为基准且只取更小值，1 行 + 1 测试。

### P1-3 query 净化误伤正常查询

`apps/bff/src/security/route-allowlist.ts:197`：
```ts
if (/(https?:|\/\/|\\|\.\.)/i.test(value)) throw ...
```
值里只要出现 `..` 就拒。**实测**（真实会话 + 假上游）：`?query=a..b` → 400，`?query=https%3A%2F%2Fapi.example.com%2Fv1` → 400；而 `nginx/1.2`、`2026-01-01T00:00:00Z`、`v1.2.3`、`api.example.com` → 200 并真触达上游。

受影响的是 6 条自由文本路由：`/logs` 与 `/logs/{logId}/body` 的 `query`、`/models` 的 `text`、`/api-keys` 的 `name`、`/channels` 的 `search`、`/oauth/accounts` 的 `filter`。前端 `LogFilters.tsx:221-228` 与 `LogBodySection.tsx:145-155` 直接暴露用户输入。

注意：**未登录时先被 401 挡下，所以匿名冒烟测不到**，只有登录后才会遇到。

**修法**：路径参数保留该检查；query 值改字符集/长度白名单，或把 `..` 规则收紧为 `^\.\./`、`/\.\.(\/|$)`。

### P1-4 login 没有 route 级 bodyLimit

`apps/bff/src/server.ts:63` 全局 5 MiB，`:162` login 注册未传 `bodyLimit`，而 `LOGIN_BODY_LIMIT_BYTES = 16 KB` 的检查在 handler 内（`controller.ts:200-224`）、排在限流与预登录校验**之后**。

**实测**：2 MiB → 403（body 已完整解析进内存），6 MiB → 413。即 2~5 MiB 区间是"先吃满再拒绝"的放大点。容器是 `read_only` + 32 MiB tmpfs，值得修。**修法**：`app.post('/webui/bff/auth/login', { bodyLimit: 16 * 1024 }, ...)`。

### P1-5 `WEBUI_TRUST_PROXY` 配错会静默降级限流

`compose.yaml:47-48` 发布 `127.0.0.1:3000:3000`，但宿主 Nginx 连进来时容器内看到的对端通常是**网桥网关**（如 `172.17.0.1`）而不是 `127.0.0.1`。照抄 `.env.example:49` 的 `WEBUI_TRUST_PROXY=127.0.0.1` → `apps/bff/src/security/ip.ts:122-141` 判定直连对端不可信 → **完全忽略 X-Forwarded-For** → 所有用户退化为共享一个限流键。

**不报错、不告警，只静默降低安全性**，而 `docs/security-model.md:74-75` 自己就警告过这一点。

有意思的是团队其实知道正确填法：真机记录里写的是 `WEBUI_TRUST_PROXY=10.30.0.0/24`（`docs/acceptance-vps-20260922.md:144`），但**没有回写到 `.env.example`**。

**修法**：`.env.example` 改成按拓扑说明（回环发布→填 Docker 网桥网关；自定义网络→填网段），并在诊断接口里输出"当前生效的可信代理列表 + 最近一次请求的解析来源"，配一个验证方法（两台不同客户端各触发一次登录失败，看限流键是否不同）。

### P1-6 首屏真传 1.62 MB：单 chunk + 全线无压缩

- 主 JS 1,624,926 B，**gzip 495 kB / brotli 398 kB 只是构建统计，线上实际传 1.62 MB** —— BFF 与两个反代片段 grep `gzip|brotli|encode|compress` **零命中**。
- 11 个页面全部静态 import（`apps/web/src/app/App.tsx:1-28`），全仓 `React.lazy|lazy(|Suspense|import(` **零命中**，vite 配置无 `manualChunks`。

**修法**：① 反代或 BFF 开 gzip/brotli（最小改动，收益最大）；② `React.lazy` 路由级分割 + `manualChunks` 把 antd / icons / react-query 拆出来。

### P1-7 没有 ErrorBoundary，一处 `toFixed` 就能白屏整站

全仓 grep `ErrorBoundary|componentDidCatch|getDerivedStateFromError|errorElement` **零命中**。而 `apps/web/src/features/overview/OverviewPage.tsx:478` 的 `metric.utilizationPercent.toFixed(1)` 没有 typeof 守卫——上游返回 null 时整站空白，用户丢失所有上下文且无恢复入口。修法：`AppShell` 内层 + 路由外层各加一个，fallback 复用现有 `ErrorNotice` 风格。

第 ③④ 项恰好是最"值得测"的部分——因为生产模式的 Cookie 前缀和安全头正是这个项目安全主张的核心，而测试**只覆盖了开发模式**。我这次手工补了生产态探针（结论：都正确），但这应该进 CI。

### P1-10 `progress` 字段类型误读（潜伏缺陷）

`apps/web/src/api/operations.tsx:102` `progress: typeof data.progress === 'number' ? data.progress : null`，而契约与上游都是对象：
```ts
// upstream-mvp.d.ts:1787 — 上游 schemas/operations.py:14-17
export interface OperationProgressData { current: number; messageCode: string; total: number; }
```
→ `typeof === 'number'` **恒 false**，progress 恒 null → `OperationTrackerPanel.tsx:19-22` 永远显示"无进度上报"；`Math.round(progress * 100)` 的 0..1 小数假定也错。

**为什么归 P1 而不是 P0**：我核对了上游真正调 `update_progress` 的生产代码只有 4 个模块共 9 处调用（`auxiliary/status_alerts.py:580`、`auxiliary/updates.py:707,866,879`、`models/upstream_sync.py:282,313,351,360`、`observability/retention.py:412`），这些 operation kind **全部不在 76 条允许清单内**；76 条里唯一的 202 同步端点 `POST /oauth/accounts/{accountId}/models/actions/sync`（上游 `routers/oauth.py:667-680` → `control.py:769` `sync_models`）走的是 `_start_operation`，只做 `mark_running/succeed/fail`，**不调 `update_progress`**。所以今天用户看不到进度丢失——因为没有任何被允许的 operation 会上报进度。但代码是错的，一旦上游给 oauth sync 或 channels discovery 加进度就静默失效。

### P1-11 `canWrite` 恒为 true，只读保护整体失效

`apps/web/src/app/AuthProvider.tsx:279-285`：
```ts
const hasWrite = capabilities.some((capability) => /write|manage|admin/i.test(capability));
```
上游 6 个能力码（`principal.py:21-30`）：`management.read`、`management.write`、`management.secrets.write`、`management.destructive`、`management.update`、`management.logs.body.read` —— **全部含子串 `management`**，正则必然命中。→ `canWrite` 恒 true，`'当前会话只具备只读能力'` 分支不可达。

实际失效面（实测清点）：5 个页面导入该 hook（`AccountsPage:116`、`ApiKeysPage:371`、`ChannelsPage:56`、`ModelsPage:117`、`OverviewPage:171`），`!canWrite` 在 **13 个文件里出现 81 次**，其中 `disabled={!canWrite}` 精确形式 17 处 —— 全部恒不生效。

安全上仍由上游 403 `CAPABILITY_DENIED` 兜底，**不是越权漏洞**，是功能失效 + 与 `ChannelsPage.tsx:9` 的声明不符。顺带一提：全仓没有任何 UI 区分 `management.destructive` / `management.secrets.write` / `management.update`，能力粒度完全没利用。

### P1-12 含斜杠的模型统计不可达

`/stats/models/{modelId:path}` 的 `:path` 语义在 OpenAPI 里无法表达（Starlette path converter），快照信息损失；BFF `route-allowlist.ts:85-99` 拒编码斜杠 → `provider/model-a` 这类 id 的统计页不可达。而这正是上游 `test_management_stats_delivery_regressions.py:78-114` 的核心场景。

根因不在任一侧写错，属于"契约格式表达不了上游能力"。建议 BFF 对这条路由放开编码斜杠（只此一条，配白名单校验），或在文档里明确记为已知限制。

### P1-13 幂等键口径 BFF 比上游宽

`apps/bff/src/routes/management-proxy.ts:43` 放行 ≤200，上游 `dependencies.py:169-171` 只接受 1..128，超了 400 INVALID_REQUEST。这是 BFF 与上游**唯一**已知的契约不一致。实际无影响（前端 `channelsApi.ts:334-339` 用 `crypto.randomUUID()`，45 字符），但注释 `channelsApi.ts:110` 写的"≤200 字符"是错误来源，应改 128。

另外：前端只有 `POST /channels` 带幂等键，其余 7 个 api-keys 写操作都没有（`ApiKeysPage.tsx:435-493`）。管理台影响有限，但要么统一加，要么在文档里写明"仅渠道创建启用幂等"。

## 五、对照上游后，"没做的事"值不值得做

README 自称"未完成"的清单我逐条核了，**列得诚实**（Telegram 批准登录、其他登录方式、高级模型元数据、负载均衡、网络诊断、MCP、多媒体日志、retention、updates/system）。补充判断：

- **不支持 Telegram 批准登录是对的**。上游 `POST /auth/sessions` 支持 `managementKey` 与 Telegram approval 两种 grant（`foundation.py:209-231`），但 Telegram 审批要拉长轮询、要处理审批超时/拒绝/取消三态，且 token 要走额外通道。当前只做 `managementKey` 一条路径，`handleLogin` 严格只接受 `managementKey` 一个字段，是**有意的范围收敛**，不是缺失。
- **不开放 updates / system 是对的**，而且实测确认白名单里确实没有（`path -match 'updates|system/'` 为空）。
- 但白名单里**留了 2 条无 UI 的写接口**：`PUT /channels/order`、`PUT /api-keys/order`（前者 `ChannelsPage.tsx:11` 明确声明不实现，后者连声明都没有）。不算缺陷，属白名单冗余，建议要么补 UI 要么移出清单。
- **允许清单本身包含删除渠道/账号/密钥、重置密钥这类高危写操作** —— 这是管理台的本分，不是越权。上游这 3 条 DESTRUCTIVE 操作（`DELETE /api-keys/{id}`、`DELETE /oauth/accounts/{id}`、`POST /oauth/actions/clear-errors`）在前端都有二次确认，符合预期。
